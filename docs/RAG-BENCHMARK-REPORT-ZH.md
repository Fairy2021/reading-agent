# StoryVerse RAG 测试总结（2026-04-22）

## 1. 测试目标

本次测试回答两个问题：

1. 当前 RAG 检索召回率（Recall）到什么水平。
2. 当前 RAG 检索性能（延迟、吞吐、防剧透约束）如何。

---

## 2. 测试对象与环境

- 测试时间（UTC）：`2026-04-22T13:31:29.739177+00:00`
- 书籍 `book_id`：`bf3ede4a-2f74-4248-b853-f83cc2dae339`（红楼梦）
- 评测章节数：`120`
- 向量分块总数：`1636`
- 平均分块长度：`516.59` 字符
- 评测 Top-K：`[1, 3, 5, 10]`
- 检索范围策略：每个 query 仅检索 `chapter_index <= 当前章节`（与线上防剧透规则一致）

---

## 3. 评测方法

本次采用两组 Query 集来测召回与性能：

1. `content_sentence`
   - 每章自动抽取一个正文句子作为 query（更接近读者“剧情提问”）。
2. `chapter_title`
   - 用章节标题作为 query（更接近“目录/主题提问”）。

核心指标：

- `Recall@K`：目标章节是否出现在前 K 条证据中。
- `MRR`：目标章节排名质量（越高越好）。
- `Latency`：检索耗时（ms）。
- `Throughput`：单线程检索吞吐（QPS）。
- `spoiler_violation_rate`：检索结果是否出现超进度章节（理想为 `0`）。

---

## 4. 测试结果

### 4.1 召回与排序质量

| Query 模式 | 样本数 | Recall@1 | Recall@3 | Recall@5 | Recall@10 | MRR |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| content_sentence | 120 | 0.9000 | 0.9667 | 1.0000 | 1.0000 | 0.9385 |
| chapter_title | 120 | 0.9167 | 0.9917 | 0.9917 | 1.0000 | 0.9495 |

结论：

- 当前 RAG 在本书上的召回已经比较稳。
- `Top-3` 召回率达到 `96.67% ~ 99.17%`。
- `Top-10` 达到 `100%`。

### 4.2 性能指标

| Query 模式 | 平均延迟(ms) | P50(ms) | P90(ms) | P95(ms) | Max(ms) | 吞吐(QPS) |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| content_sentence | 7.477 | 7.567 | 9.719 | 10.011 | 11.320 | 133.590 |
| chapter_title | 6.788 | 6.757 | 8.840 | 9.356 | 11.036 | 147.135 |

结论：

- 检索层延迟在毫秒级，`P95` 约 `9~10ms`。
- 当前单线程检索吞吐约 `133~147 QPS`，对个人项目初版足够。

### 4.3 防剧透约束

| Query 模式 | spoiler_violation_count | spoiler_violation_rate |
| --- | ---: | ---: |
| content_sentence | 0 | 0.0000 |
| chapter_title | 0 | 0.0000 |

结论：

- 在本次评测中，检索层没有出现超出读者章节进度的证据，防剧透约束有效。

---

## 5. 结果解读（你现在可以怎么用）

1. 你可以把默认 `rag_top_k` 保持在 `6`（当前配置）继续推进产品。
2. 角色对话页显示 `3~5` 条 citation 就足够，召回覆盖已经较高。
3. 现在的主要瓶颈已不在“召回”，而在“语义理解与角色表达质量”（即 LLM 层和角色状态层）。

---

## 6. 评测边界与风险

这份结果是“当前系统能力”的真实快照，但有边界：

1. 目前 embedding 是本地 deterministic embedding（哈希向量），非真实语义模型。
2. 当前 query 仍以章内句子/标题为主，对“高度抽象问法”尚未单独建集评估。
3. 本次是单本书（红楼梦）评测，跨书泛化仍需要继续测。

---

## 7. 下一步建议（按收益优先级）

1. 增加一组“读者自然问法”评测集（例如 200 条），单独统计 `Recall@K`。
2. 接入真实 embedding API（保留当前接口不变）并做 A/B 对比报告。
3. 增加 rerank 层（cross-encoder 或 LLM rerank），重点优化 `Recall@1`。
4. 把评测脚本接入 CI，确保后续 skill 迭代不回退召回率。
